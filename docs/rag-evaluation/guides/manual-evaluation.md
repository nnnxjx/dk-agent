# RAG 人工评测实操指南

这份指南帮助你自己核对题库、检索结果和最终回答，并留下可复核的人工判断。可以直接复核已经保存的结果，也可以从页面手动发起查询；不需要让 LLM 替你打分。表格和代码只负责存储、算术汇总，判定由评测人完成。

当前范围：107 道有答案题，81 道开发题、26 道保留测试题。先用开发集练习和修订规则，暂不使用保留测试集调参。本指南不要求新增无答案题；有答案题仍要记录误拒答。

## 1. 第一次做，从这四个动作开始

1. 打开 [题库阅读版](../../../datasets/rag/project-docs/v1/questions.md)，选一道开发题，先读对应的冻结原文，确认答案和必要证据。
2. 找到同题两种策略的结果，只看实际返回片段和最终回答，先不看 `judgment`、`rawJudgment` 和已有总分。
3. 用本文模板逐条填写证据覆盖、要点覆盖和事实支持，并注明原文位置与理由。
4. 完成人工判断后，再看自动标签，记录分歧；不要直接照抄模型理由。

可以先练习 `project-043`（删除会话接口）。它展示了“依据来自资料，但答案仍可能不完整”的情况，完整示例见第 6 节。这是练习案例，不能当成随机样本成绩。

## 2. 明确自己要评什么

| 工作 | 你要判断什么 | 主要依据 |
| --- | --- | --- |
| 题库审核 | 标准答案、要点和证据是否正确、完整 | 全部冻结原文及适用范围 |
| 检索评测 | 最终 TopK 是否包含回答必需的证据 | 经审核的证据组与实际 TopK |
| 回答正确性 | 核心结论、数字、接口等是否正确 | 经审核的参考答案与原文 |
| 回答完整性 | 必要要点覆盖了多少 | 事先固定的要点清单 |
| 回答忠实度 | 回答中的事实是否有当次检索依据 | 当次实际交给 Agent 的片段 |

**正确性允许查完整原文；忠实度只能看当次实际提供给 Agent 的证据。**正确答案不一定有当次依据，忠实复述一份简略或旧资料也不保证回答正确。

先写下评测范围，例如：“复核 81 道开发题中随机抽取的 10 道及 10 道诊断题，两组使用相同问题，仅依据内部知识库”。不要在看完分数后临时改规则。

同题问答文件为 `answers-project-043.json`：

| 字段 | 人工怎么看 |
| --- | --- |
| `trace.answer` | 最终回答，正确性、完整性与事实拆分的对象 |
| `trace.contexts` | 多次工具调用实际返回的片段；忠实度判断依据 |
| `trace.contexts[].sources` | 合并去重后的全部来源，用知识库 ID＋Chunk ID 追踪，不只看来源名称 |
| `toolExecutions` | 实际检索 query、TopK、调用是否完成 |

当前跨库固定检索仍用来源＋原文匹配，不应假定它已有逐题 Chunk ID 绑定。你可以在人工表中记录观察到的实际知识库 ID、Chunk ID；不要直接改历史绑定文件。

**固定 TopK 检索与 Agent 问答是分别运行的。**Agent 可以改写 query、多次检索、选择其他 TopK。不能拿固定 Top3 文件当作另一轮 Agent 回答的唯一上下文。

## 4. 第一步：先人工审核标准

逐题核对以下事项，再看检索排名：

1. 问题是否清楚，是否确实能由当前冻结资料回答？
2. 参考答案有没有错字、漏条件、错误的 HTTP 方法或路径参数？
3. 每条必要要点是否被原文支持，来源是否适用？
4. 同一事实是否有其他等价支持来源？多条引用是替代关系，还是必须组合？

例如，同一事实出现在 Chunk A、B，A 或 B 即可支持，这是同一组中的 OR；另一个必要事实在 Chunk C，则需“第一组 AND 第二组”同时满足。不要把两份等价来源误设成必须都检索回来。

需要增加替代来源时，独立阅读完整冻结语料，记录原文与理由；可以先汇集多种算法候选辅助发现，但不能只把某算法的 TopK 当作全部真值。其他位置仍可能有未发现的相关证据。

已有 `points` 有时一条包含多个事实。如果要拆成更细的原子要点，先对选定题目统一审核、冻结为新的人工评分版本；两种策略都用同一版本。不要给一种算法用旧清单、另一种用新清单，也不要将新人工完整性直接当成与旧自动完整性完全同口径。

发现题目歧义、原文冲突或答案标签错误，记为“标签待修订”，不要强行给算法判错。保留原数据，用新版本统一重算所有对照组；报告修订数和不可评分题数，不悄悄删掉难题。

## 5. 第二步：人工评检索

### 5.1 逐条证据核对

对每条必要事实，读 TopK 的全文和来源，填写“有／无／待确认”：

- 必须是适用对象、条件和版本下的证据。其他系统的相同数字不算。
- 不能忽略否定词，例如“不支持自动切换”不能支持“支持自动切换”。
- 允许合法改写和等价来源，不要求逐字相同；若超出现有标签，先记录为“待审核替代证据”，不要一边评一边静默扩大标准。
- 同一证据重复出现只算一次。多处证据组合时每组都检查。

纯粹“提到了关键词”或“与话题相关”不能算可支持答案。人工若使用 0/1 标签，建议 1 表示能支持对应必要事实，0 表示不能；拿不准时保留待确认，交第二位评测人复核。

### 5.2 人工计算指标

假设两条必要证据，Top5 只找到第一条：

```text
证据 Recall@5 = 已覆盖必要证据组数 / 必要证据组总数 = 1/2 = 50%
Hit@5 = 1（至少一组命中）
完整证据命中 = 0（没有找齐全部组）
```

若还要复核步骤一的 Chunk 指标，先审核 `binding.json` 的标准 Chunk ID：

```text
Chunk Recall@K = 找回的标注相关 Chunk 数 / 标注相关 Chunk 总数
Precision@K = 前 K 条中标注相关 Chunk 数 / K
单题 RR@K = 1 / 首个相关 Chunk 的排名；未命中记 0
```

去重后计数，只检查前 K 条。沿用现有脚本时，返回不足 K 条也以 K 为 Precision 分母。不能只看返回的 TopK 就断定知识库中总共有几个相关 Chunk；若没有审核完整相关集合，应将结果称为“相对于当前标签的 Recall”。

跨库去重结果可能含多个源 Chunk；做跨库检索的人工主指标时建议按证据组计数，避免把一条结果的多个来源随意当作多条 Precision 分子。不要把单库 Chunk Recall 和跨库证据 Recall 混用。

### 5.3 判断“合并丢证据”

同一条标准证据，在 `candidates[].hits` 中存在，但在 `output.results` 中缺失，才记为合并后丢失。各库候选中就没有，是召回阶段未找到。

如果原文仅仅换到了另一个等价来源，先记录标签问题，不能仅据严格来源匹配失败就认定资料完全丢失。已有案例见 [复核记录](../results/step4-expanded/review.md)。

## 6. 第三步：人工评回答

建议先盲评：让另一位同学将两组结果标为 A/B，或复制答案与上下文并隐藏配置名、排序分数、模型判分。每题随机交换 A/B 顺序，先写自己的判定，再揭晓策略。单人评测也尽量先隐藏自动分数。

### 6.1 正确性

对照审核后的标准答案，检查核心事实是否正确，是否存在实质错误。建议预先约定：“所有核心要点正确且没有实质错误”为通过；普通格式差异不扣分。有答案题误拒答、接口漏关键参数、适用对象错误均应判为不通过。非核心信息遗漏通过完整性反映。

原合并组真实案例 `project-043`：

- 问题：删除会话使用哪个接口？
- 标准答案：`DELETE /api/v1/chat/conversations/:id`。
- 实际回答：`DELETE /api/v1/chat/conversations`，并引用概览表。
- 人工结论：遗漏 `:id`，核心接口不完整，正确性不通过。不能因为回答里出现 DELETE 和 conversations 就通过。

可直接打开 [这份回答](../../../reports/rag-baseline/step4-expanded/project-step4-v1-no-rerank-20261128/answers-project-043.json) 与 [冻结 API 原文](../../../datasets/rag/project-docs/v1/corpus/api.md) 核对。

### 6.2 完整性

按照事先固定的要点逐项标记，不凭“整体看起来不错”打分：

```text
单题完整性 = 已覆盖的必要要点数 / 预先固定的必要要点总数
```

例如模型名与向量维度是两个独立要点，只说模型名则为 1/2。只有在本轮人工规则事先把它们拆成两项时，才能这样计数；若沿用旧清单的一条组合要点，就应按旧规则评价并注明粒度。不要现场改变分母。

### 6.3 忠实度

1. 将最终回答拆为最小的、可核实的事实陈述，不把一句含三个事实的话当一条。
2. 每条与 `trace.contexts` 核对，标记“支持／不支持／待确认”，写明支持片段的来源与 Chunk ID。
3. 不要求答案复述原文，合理的跨片段组合可以算支持；但“语义相近”“我知道它是真的”不能代替证据。
4. 礼貌、标题、纯格式不算事实；重复表达同一事实按同一套规则去重，不靠堆重复句提高支持比例。

| 示例陈述 | 当次实际片段 | 判定 |
| --- | --- | --- |
| 使用 BGE-M3 | 明确记载 BGE-M3 | 支持 |
| 向量维度为 1024 | 明确记载 1024 维 | 支持 |
| 可以自动切换模型 | 当次片段没有说明 | 不支持，即使别处资料或你的知识认为是真的 |

```text
单题忠实度 = 有证据支持的事实陈述数 / 提取的事实陈述总数
上例 = 2/3 = 66.67%
```

只检查引文文字出现，不足以证明结论被支持。例如引用“不支持自动切换”中的“支持自动切换”，程序可能匹配通过，但人工应判不支持。反过来，合法的概括或组合原文可能不满足连续子串匹配，人工可以给出明确的证据推理并判支持。

project-043 也说明：概览表确实写了简略接口，回答可能忠实复述片段，仍未满足完整接口的正确性要求。**忠实度高不等于答案正确。**

如果只有“无法确认”等纯拒答，没有实质事实陈述，忠实度记 N/A，不默认 100%；同时记录有答案误拒答。关于“资料中没有记载”的强断言，先区分它是单纯承认自己没找到，还是在声称已穷尽整个语料；不要把未检索到自动等同于知识库不存在。

## 7. 如果想完全手动发起查询，而非只复核已有结果

可以使用项目页面，参考 [项目启动说明](../../../README.md)。按以下流程记录：

1. 在自己有权限的测试租户中准备知识库，只上传冻结的 `corpus` 原文，保持模型与分块设置一致，不上传题库或答案。
2. 单库评测时把 7 份文档放在同一库，在知识库搜索页用相同 query 分别选择 Dense、BM25、Hybrid 和相同 TopK；保存实际片段、排名及来源。
3. 跨库评测时使用同一批文档的分库布局，并确认服务端开关分别为原合并／重排。一次只改变待比较因素；不要在评测中途同时换模型、改问题和调整分块。
4. 问答每题新建会话，用同一问题及同一知识库约束发问，保存最终回答和每次工具调用的实际结果。
5. 如果触发联网搜索，另标为允许联网场景；不要混入纯知识库评测。无法确认知识库范围时，也不能宣称它与受控脚本同条件。
6. 按第 4～6 节人工标注。耗时可另外记录，但手动等待不作为服务端 P95 的严谨测量。

当前脚本创建的知识库属于专用评测租户，普通登录账号可能看不到。复核已有文件不需要该租户登录；在自己租户重建时，知识库及 Chunk ID 会改变，需重新关联标签，不能照抄旧 binding 的 ID。

如果页面没有暴露实际检索片段，仍可评正确性与完整性，但忠实度应记“上下文不可得，未评”，先补齐工具结果或执行记录；不能拿整份原文冒充当次上下文。页面手测与当前直接 AgentService 的脚本在鉴权、持久化等覆盖范围也不同，报告需分别写清。

## 8. 评多少题，如何避免只挑成功案例

- 练习：先选 3～5 道开发题，覆盖精确接口、数字、多处证据和已知争议，统一规则，不拿练习成绩作总体准确率。
- 抽样复核：例如随机抽 10 道开发题，再选 10 道错误或争议题；先固定 ID、抽样方式和名单。两种策略必须评相同题，保留抽样时间及随机方法／种子（如有）。
- 分别报告“随机样本结果”和“诊断题发现”。错误定向抽样不能估计整个 81 题的准确率，随机小样本也有不确定性，不外推为全量已人工通过。
- 全量人工评测：81 题两种策略共 162 份回答；固定 Top5 跨库检索也是两组各 81 题。未全量评完就只报告已评数量，不能把未评分题默认为通过。
- 第二位评测人可独立评同一部分题，在讨论前保存各自标签；再对分歧逐项裁决。记录原始一致率及分歧数，不用讨论后的统一标签冒充独立一致性。

26 道保留测试题用于标注审核与方案冻结后的最终验收，不用来练习调参。看过其失败并据此优化后，应记录使用并补充新的保留题。

## 9. 可复制的人工记录模板

建议在本地 `reports/rag-baseline/manual-review/日期/` 保存 Markdown 或 CSV，作为与自动报告并列的人工记录。以下是空白模板，不表示已经评过任何样本。原始回答、自动标签和历史报告不覆盖。

### 9.1 一轮评测的说明

```text
人工评测版本／日期：
评测人／第二评测人：
目的：题库审核／检索比较／问答比较／自动评分复核
语料版本、题库版本、代码版本：
模型、分块、检索模式、TopK、重排设置：
运行结果目录／页面操作记录：
抽样方式、固定题目 ID、样本数：
A/B 对应策略（盲评完成后填写）：
是否允许联网、实际知识库范围：
评分规则版本；是否调整旧 points、替代证据：
已评／待评／待裁决／运行失败／上下文缺失数量：
```

| 题目 ID | A/B | TopK | 必要证据组 | 标准原文及来源 | 返回库 ID／Chunk ID／排名 | 有／无／待确认 | 理由／是否替代来源待审 |

另附本题证据 Recall、完整证据是否命中；如评 Chunk 指标，附审核后的相关 ID 全集及命中 ID，不能只填百分比。

### 9.3 每题回答与要点

| 题目 ID | A/B | 要点编号及内容 | 覆盖／未覆盖／待确认 | 回答中的对应句 | 理由 |
| --- | --- | --- | --- | --- | --- |

## 10. 如何汇总，以及怎样写结论

```text
人工核心正确率 = 判为正确的题数 / 本轮确定纳入的有答案题数
总体完整性 = 每题要点覆盖比例的平均值
证据 Recall 宏平均 = 每题证据组覆盖比例的平均值
完整证据覆盖率 = 找齐全部必要证据的题数 / 纳入的题数
总体忠实度 = 可评且有事实陈述的各题忠实度的平均值
有答案误拒答率 = 错误拒答的有答案题数 / 本轮纳入的有答案题数
```

忠实度按题平均，不把所有事实合在一起算成另一个分数。空事实 N/A、上下文缺失、运行失败和未评题数量要同时报告。运行失败在面向系统的正确率和完整性中记 0；如果另报“成功运行样本中的质量”，必须明确分母，不能代替包含失败的主结果。

待裁决项先保留，不默认为通过；正式发布前完成裁决。若必须发布阶段结果，报告数量及上下界或未决状态，不静默排除来提高分数。无法人工评估忠实度的题不强行记 0 或 1，报告忠实度覆盖题数，避免遗漏被隐藏。

人工评分规则若与自动脚本不同，明确标为新协议，不直接用两者分数差代表算法提升。标签被修订后，两种算法的旧结果应使用同一新标签重新统计，旧版报告仍保留。

报告可以写：“在固定的 20 道开发题中完成人工复核，其中 10 道随机样本、10 道诊断样本；发现若干标签或评分分歧，详细记录见逐题表。”只有实际完成全量时，才能写“81 题两组结果均经过人工评测”。不要把阅览了若干例子表述成整套系统已人工验收。

## 11. 完成一轮的自查

- 题目名单和规则在看结果前固定，两种策略使用同一问题与标准。
- 查过原文上下文，尤其对象、否定词、数字和接口参数。
- 正确性与忠实度的依据没有混用，各次运行的上下文没有串用。
- 每个要点、事实判断有出处与理由；待确认和缺少上下文没有被隐去。
- 自动标签在人工初判完成后才用于分歧分析。
- 样本数、失败、未评、忠实度覆盖数及抽样限制写清，结论不超出已评范围。
- 没有上传题库和答案到知识库，没有改写原始回答和历史评分。
