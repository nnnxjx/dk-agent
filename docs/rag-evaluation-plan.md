# RAG 评测实施记录与后续计划

记录日期：2026-11-26。

本文记录当前项目的 RAG 评测基础、后续实施步骤及验收方式。现有数值来自仓库历史报告，本次整理文档没有重新运行评测，也没有执行下面的待办。

## 1. 评测目标与范围

RAG 的基本链路为：文档解析、分块和入库 → 检索相关片段 → Agent 使用工具结果 → 生成最终回答。

需要分别验证：

- 文档处理：内容是否完整，分块是否切断关键依据。
- 检索：是否找到正确资料，是否找齐必要证据，排序是否合理。
- 回答：是否正确、完整、有依据，该拒答时是否拒答。
- 系统：工具调用是否合理，跨库合并是否保留证据，租户隔离、失败处理、耗时和成本是否符合要求。

检索命中率不等于最终回答正确率，各层指标应分别报告。

## 3. 指标口径

### 3.1 检索指标

| 指标 | 计算与解释 |
| --- | --- |
| Hit@K | 有答案问题中，前 K 条至少命中一个相关片段的问题比例 |
| Recall@K | 每题找回的标注相关片段数 / 全部标注相关片段数，再对有答案题取平均 |
| Precision@K | 每题前 K 条中相关片段数 / K，再取平均；不足 K 条时仍按 K 作分母，并在报告注明 |
| MRR@K | 首个相关片段名次的倒数，再对有答案题取平均；未命中记 0 |
| 完整证据命中率 | 前 K 条覆盖全部必要证据组的问题比例；同一证据组命中任一可支持它的片段即可 |
| nDCG@K（可选） | 标注不同相关等级后，评估相关程度和排序位置 |

旧基线说明将“至少命中一个片段”的比例称为 Recall，严格来说应叫 Hit@K。当前 Hybrid 脚本的 `hitAt5` 命名正确。

例如：一题有 3 个标注相关片段，Top5 找回其中 2 个，首个正确片段排第 2，则 Hit@5=1、Recall@5=2/3、Precision@5=2/5，对 MRR 的贡献为 1/2。如果缺失片段是必要证据，则完整证据命中为 0。

相关片段召回率与必要证据覆盖率应区分：重叠分块可能都包含同一份证据，不必把所有重复片段找回来才能回答。

### 3.2 回答与工程指标

| 指标 | 评估内容 |
| --- | --- |
| 正确性 | 是否符合参考答案与事实，接口、数字、错误码是否准确 |
| 忠实度 | 回答中的事实性陈述能否由当次检索上下文支持 |
| 完整性 | 是否覆盖参考答案的必要要点 |
| 回答相关性 | 是否回答用户问题，有无跑题 |
| 引用正确率 | 引用来源能否支持对应结论；同时记录是否提供引用 |
| 无答案拒答率 | 无答案题中，明确说明依据不足且未编造答案的比例 |
| 有答案误拒答率 | 有答案题中，错误拒绝回答的比例 |
| 工具调用合理性 | 需要知识库时是否调用检索，查询内容是否正确 |
| 延迟 | 分别报告检索、首字、最终完成耗时的 P50/P95 |
| 稳定性与成本 | 失败率、超时率、Token、调用次数及单次回答成本 |
| 隔离性 | 是否出现其他租户的内容；泄漏应作为阻断问题处理 |

接口路径、错误码、数字等尽量使用规则检查；开放回答可以使用人工或 LLM 评分。LLM 评分应固定模型、提示词与评分量表，并抽样人工复核。没有引用能力时先记录缺失情况，不把它当作已经实现的能力。

参考：[Ragas 官方指标说明](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)。采用具体指标实现前应确认其版本和计算口径，不把普通 Precision@K 与框架的 Context Precision 自动视为同一指标。

## 4. 第一步：补齐检索方案对比

状态：首轮九组对比已完成（2026-11-26）。统一对比脚本、Recall/Precision 计算与测试已完成，Dense、BM25、Hybrid 各 Top3/5/10 均已实测。

### 实施内容

1. 固定语料版本、证据标注、分块参数、Embedding 模型、分词器和运行环境。
2. `hybrid-eval.mjs` 已支持选择 `dense_v2`、`bm25`、`hybrid` 和 TopK，`compare` 可运行三种模式与 Top3/5/10 的九组配置。
3. 在同一开发集上对比三种模式及 Top3、Top5、Top10。
4. 报告 Hit@K、Recall@K、Precision@K、MRR@K、完整证据命中率、P50/P95、失败数。Recall 和 Precision 均为必测指标，按第 3 节口径对有答案题取宏平均；失败题记 0，无答案题单独统计。
5. 按同义改写、错误码、接口路径、中英文混合等类别分析失败题。

### 验收与产物

- 三种模式使用同一题库和证据口径，保存逐题结果、参数和汇总表。
- 模式对比时保持其他因素不变；不能仅凭 Hybrid 单次成绩断言优于 Dense。
- 失败请求纳入质量指标的失败处理，并单独报告失败数；存在调用失败时先排查，再判断方案优劣。
- 修改分块参数时重新绑定证据与 Chunk ID，不复用失效主键。

脚本运行示例，仅适用于对应知识库和依赖已经准备好的环境：

```powershell
node --env-file=.env scripts/rag/hybrid-eval.mjs prepare dev "RAG 评测 v2" reports/rag-baseline/hybrid-v2
node --env-file=.env scripts/rag/hybrid-eval.mjs evaluate dev "RAG 评测 v2" reports/rag-baseline/hybrid-v2
```

`prepare` 会重新写入本地绑定文件。正式实验使用新的输出目录保存记录。多模式对比与单配置命令：


## 5. 第二步：补齐最终回答评测（优先）

状态：首轮受控 HTTP/SSE 端到端基线已完成（2026-11-26）。五题先导和完整 30 题开发集均已运行；不包含真实登录与持久化验证。

### 实施内容

1. 沿用现有 40 题和参考答案，通过实际聊天接口运行。
2. 记录每题的 Agent 路由、是否调用 `rag_retrieval`、实际检索 query、工具参数、检索片段与来源、最终回答。
3. 增加正确性、忠实度、完整性、拒答评分，记录耗时、Token、成本和错误。
4. 将知识库问答和允许联网的完整 Agent 场景分开运行，明确 `web_search` 是否允许使用。
5. 固定生成模型、提示词、温度等配置，必要时重复运行以观察波动。

### 重点案例

问题：“系统在 1000 个并发用户下的 P95 延迟是多少？”

固定语料没有该压测数据。合格回答应说明缺少依据，即使检索返回了一些片段，也不能据此编造具体延迟。

### 验收与产物

- 保存逐题 trace 和评分理由，能够区分检索失败、证据丢失、生成错误、工具未调用等原因。
- 有答案题与无答案题分别报告，避免大量拒答掩盖回答能力不足。
- 为必要要点建立明确评分规则，LLM 评分抽样人工复核。
- 产出端到端报告，明确不再仅用检索命中率代表最终回答质量。

## 6. 第三步：增加跨知识库评测

状态：首轮合成跨库集成评测已完成（2026-11-27）。使用真实 SQL、Milvus、检索工具和 Agent；真实业务语料扩充仍属于后续工作。

真实 Agent 工具固定使用 Hybrid，跨库检索后按库内名次轮流合并并去重。它与现有单库评测的路径不同，不能直接用单库结果代表跨库效果。

| 场景 | 验证目标 |
| --- | --- |
| 一个库有答案，其余库有干扰资料 | 正确证据能否进入最终 TopK |
| 需要两个库的资料共同回答 | 最终结果是否覆盖两处必要证据 |
| 多库存在相同文本 | 去重后是否保留完整来源 |
| 部分库查询失败 | 是否明确标记部分失败，其他结果是否仍可使用 |
| 所有库查询失败 | 是否准确报告失败，最终回答是否避免编造 |
| 不同租户有相似内容 | 是否始终不返回其他租户内容 |

### 验收与产物

- 通过真实 `rag_retrieval` 路径执行，而非仅调用单库搜索。
- 同时记录各库候选和最终合并结果，分析关键证据是否在合并时丢失。
- 报告最终 TopK 的命中率、完整证据覆盖率和端到端回答结果。
- 不使用不同库的 `localScore` 直接比较全局相关性。
- 租户隔离、部分失败、去重来源保留均有独立案例和结果。

### 自动评分与边界

自动评审会将参考答案拆分为要点，检查正确性、完整性、相关性、拒答，并逐条判断事实陈述是否由实际检索片段支持。支持性引文会在脚本中再次精确匹配实际片段，不用参考答案补足忠实度证据。

当前评审和生成使用同一配置模型，因此成绩仅是待人工复核的自动估计，不是独立客观真值。参考答案拆点也尚未逐题人工预审，首轮需审查要点是否合理并固定下来。引用正确率尚未自动实现，需根据生成输出补充来源与结论对应关系的人工检查。

回答正确性、完整性和无答案拒答率以全部相应题目为分母，失败或未评分题记 0，同时单独展示运行失败数和评分失败数。忠实度只对成功评分且有事实陈述的回答计算，误拒答率只对成功评分的有答案题计算；不能脱离评分覆盖率解读。

生成链路暂未暴露可靠 Token/费用信息，明确记录为不可用；评审模型返回的 Token 用量单独保留，不能代替整条链路成本。
